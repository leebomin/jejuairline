## 1. 왜 구조를 이렇게 크게 바꿨나

v1.0 → v1.1까지는 "앙상블(GBM+RF+MLP) + CNN-LSTM을 따로 학습해서 비교"하는 구조였다. 이 구조로는 아래 세 가지가 어려웠다.

1. RUL 숫자만 나오지, **얼마나 확신할 수 있는지(불확실성)** 는 알 수 없다.
2. RUL 예측과 별개로 **어느 부품이 고장났는지**는 전혀 모델링하지 않았다.
3. 모델을 4~5개 따로 학습해야 해서 비용이 크고, 서로 다른 모델이 같은 신호를 다르게 해석한다.

그래서 v2는 트리 모델과 CNN-LSTM을 나란히 비교하던 방식을 버리고, **CNN 하나가 여러 출력(RUL·고장부위·열화시작·건강지표)을 동시에 예측**하는 멀티태스크 구조로 완전히 바꿨다. N-CMAPSS가 원래 제공하는 θ(모듈별 건강 파라미터)를 학습 라벨로 추가 활용한 것도 이번이 처음이다.

---

## 2. 8단계 구조

| 단계 | 이름 | 하는 일 |
|---|---|---|
| 1 | 데이터 통합 + θ·hs 읽기 | DS01/02/03 h5 파일 전체(dev+test)를 하나의 pool로 합침. 유닛 번호에 파일별 offset을 더해 엔진이 서로 안 겹치게 함. 기존엔 안 읽던 θ(건강 파라미터), hs(열화상태 플래그)까지 읽음 |
| 2 | θ → 라벨 생성 | θ를 "모듈별 열화량"(건강지표 회귀 정답)과 "가장 많이 닳은 모듈 1개"(고장부위 분류 정답)로 변환 |
| 3 | Regime 정규화 + 잔차 | 운항조건(W)을 KMeans로 8개 regime으로 묶고 그룹별로 센서를 표준화. 건강 기준선 대비 잔차를 추가 특징으로 붙임. **fold의 train 유닛에만 통계를 fit**해서 v1.1에서 고친 데이터 누수 원칙을 그대로 유지 |
| 4 | 멀티헤드 CNN | Conv1d 3층(커널 7→5→3) → AdaptiveAvgPool → 공유 FC → 5개 출력 헤드(RUL 평균 `mu`, RUL 로그분산 `lv`, 고장분류 `fault`, 열화시작 `hsh`, 모듈별 열화량 `theta`) |
| 5 | 불확실성 + 딥앙상블 | `lv`를 함께 학습해 가우시안 음의로그가능도(NLL)로 최적화(초반 5에폭은 MSE로 워밍업). fold마다 시드가 다른 모델 3개(`ENSEMBLE_M`)를 학습해 평균 → 딥앙상블 |
| 6 | 고장 분류 붕괴 방지 | 흔한 고장 모듈만 계속 찍는 붕괴를 막기 위해 클래스 가중치 적용 + θ 기반 argmax(원본/모듈별 z정규화) 등 3가지 방법을 다수결 baseline과 비교 |
| 7 | Conformal 예측구간 | 검증 잔차의 (1-α) 분위수로 "RUL ± Q" 구간을 만듦. 비행클래스별 조건부 적용, fold-out 방식으로 실제 커버리지 측정 |
| 8 | 체크포인트 실행 | `prepare()`(fold 분할, `meta.pkl`로 캐시) → `run_fold(k)`(fold 하나, 모델 하나씩 저장) → `finalize()`(전체 집계 + JSON 저장). 중간에 세션이 끊겨도 끝난 fold/모델은 재학습 없이 즉시 이어감 |

## 3. v1.1과의 구조 비교

| 항목 | v1.1 (`v1.1_partial_run.ipynb`) | v2/v12 (`8stage_*.ipynb`) |
|---|---|---|
| 모델 수 | GBM + RF + MLP + CNN-LSTM (개별 학습 후 비교) | 멀티헤드 CNN 1개 (fold당 3개 시드 앙상블) |
| 출력 | RUL 점 예측만 | RUL 평균+분산, 고장부위, 열화시작, 모듈별 열화량 — 4종 동시 |
| 불확실성 | 폴드 간 표준편차로만 간접 확인 | 모델이 직접 분산(`lv`)을 학습 + conformal 구간(커버리지 측정) |
| 정규화 | MinMaxScaler (전역 스케일) | 운항조건 기준 8-regime 정규화 + 건강기준선 잔차 |
| 데이터 범위 | 파일별로 dev만 사용, 클래스별로 따로 처리 | 전체 파일 × dev/test를 하나의 pool로 통합 |
| 데이터 누수 방지 | 폴드 내부에서 스케일러 fit (v1.1에서 고침) | 동일 원칙 유지 (regime 통계·정규화 전부 train 유닛에서만 fit) |
| 재현/재개 | 결과를 조합별 pickle로 저장 | fold·모델 단위 체크포인트, `meta.pkl`로 fold 구성 고정 재현 |
| RUL 상한(CAP) | 125 고정 | **50 버전 / 125 버전 별도 파일**로 분리 실행 (아래 4번 참고) |

## 4. CAP=50 vs CAP=125

두 노트북은 `CAP` 값(1개 상수)과 그에 딸린 저장 경로만 다르고 **나머지 코드는 완전히 동일**하다.

| | `8stage_cap50.ipynb` | `8stage_cap125.ipynb` |
|---|---|---|
| `CAP` | 50 | 125 |
| 체크포인트 폴더 | `v12_ckpt_cap50` | `v12_ckpt_cap125` |
| 결과 폴더 | `v12_결과_cap50` | `v12_결과_cap125` |

CAP은 "RUL이 이 값보다 크면 전부 이 값으로 자른다"는 상한이다. CAP이 작을수록 모델은 "수명이 얼마 안 남았을 때"의 구간에 더 집중해서 학습하게 되고, CAP이 클수록 "아직 여유 있는" 구간까지 넓게 본다. **두 버전의 RMSE는 스케일 자체가 다르므로 직접 비교하면 안 된다** — 이 부분은 노트북 상단 안내에도 명시돼 있다. 어느 CAP이 더 실전(제주항공 LCC 정비 주기)에 맞는 값인지는 두 버전을 모두 실행한 뒤 별도로 판단해야 한다.

```
L(윈도우 길이)=50, DOWN(다운샘플)=10, STRIDE(윈도우 간격)=20

```

## 7. 실행 방법 요약

1. Colab에서 정의 셀을 전부 위→아래로 실행
2. `meta = prepare()` — pool 로드 + fold 분할 (한 번 하면 `meta.pkl`로 캐시됨)
3. `fold_status(meta)`로 진행 상황 확인(선택)
4. `for k in range(len(meta['folds'])): run_fold(k, meta)` — 전체 fold 처리, 끊기면 셀만 다시 실행하면 이어짐. 하루에 하나씩만 돌리고 싶으면 `run_fold(0, meta)`처럼 fold 번호를 하나씩 지정해도 됨
5. 모든 fold가 끝나면 `result = finalize(meta)`로 최종 지표 계산 + JSON 저장
6. CAP=50, CAP=125 두 노트북을 **각각** 이 순서대로 실행 (체크포인트 폴더가 분리돼 있어 서로 섞이지 않음)
