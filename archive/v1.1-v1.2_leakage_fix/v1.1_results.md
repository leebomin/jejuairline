## 1. 이 버전을 만든 이유

`team_comparison.md`에서 팀원에게 남겼던 질문 중 1번(**"LCC 보정 효과가 매뉴얼의 절반밖에 안 나오는 이유"**)을 스스로 다시 확인한 결과, 원인은 방식 차이가 아니라 **평가 코드 자체의 데이터 누수**였다는 걸 확인했다. 그래서 v1.0 코드를 처음부터 다시 점검하면서 발견한 문제를 전부 고친 버전이 v1.1이다.

## 2. 피드백 대응표 (F1–F5)

| # | 피드백 | 문제 | 반영 위치 |
|---|--------|------|-----------|
| F1 | LCC 개선율이 30%→15%로 반토막 | 원인이 방식 차이가 아니라 데이터 누수였을 가능성 | F5로 누수 원인 차단 + `lcc_cv()`에서 동일 프로토콜로 가중치(1/3/5/10) 스윕 재검증 |
| F2 | 단거리 결과의 폴드 편차가 큼 | 모델이 불안정한 게 아니라 애초에 단거리는 엔진이 2~3개뿐이라 편차가 클 수밖에 없음 | `cross_val()`이 평균과 함께 **표준편차·엔진 수**를 같이 반환/출력하도록 수정 |
| F3 | GPU 미사용 + 샘플 수 제한 | Colab에서 CPU로만 돌고 있었고 `MAX_SAMPLES=30000`으로 일부 데이터만 사용 | 모델을 `DEVICE`(GPU)로 이동, `MAX_SAMPLES=None`으로 제한 해제 |
| F4 | MLP는 `sample_weight`를 지원하지 않음 | 기존 코드는 LCC 가중 학습에 MLP도 포함시켜서 가중치가 실제로는 적용 안 됐을 가능성 | 가중 학습 대상에서 MLP 제외, **GBM+RF만** 가중 학습 |
| F5 | 스케일러/특징 선택을 전체 데이터로 fit | `MinMaxScaler`, `SelectKBest`를 train+test 합쳐서 fit → 테스트 정보가 학습에 새어 들어감(데이터 누수) | 전처리 단계에서 스케일링을 떼어내고, 교차검증/LCC 루프 **내부에서 train 폴드에만** fit하도록 재구성 |

## 3. 추가로 잡은 버그 (B1–B5)

| # | 버그 | 증상 | 수정 |
|---|------|------|------|
| B1 | BatchNorm + 마지막 배치 크기 1 | 특정 폴드에서 학습이 죽음 | `DataLoader(drop_last=...)` 가드 추가 |
| B2 | `forward()`의 `.squeeze()`가 0차원으로 붕괴 | 배치 크기 1일 때 shape 에러 | `.squeeze(-1)`로 축 지정 |
| B3 | PyTorch 시드 고정 안 됨 | 같은 코드를 다시 돌려도 결과가 매번 바뀜 | `seed_everything(42)` 추가 |
| B4 | 추론 시 전체 텐서를 GPU에 한 번에 올림 | 큰 데이터셋에서 OOM 위험 | 배치 단위 추론으로 변경 |
| B5 | 윈도우 배열이 float64로 쌓임 | 메모리 낭비 | float32로 캐스팅 |

## 3-1. 그 밖의 구조 변경

- **엔진(유닛) 단위 교차검증(LOO-CV)** 을 GBM/RF/MLP/앙상블/CNN-LSTM 전부에 일관 적용 (v1.0은 실험별로 평가 방식이 조금씩 달랐음)
- 데이터셋·비행클래스별로 **결과를 개별 pickle로 저장**(`get_or_run_class`) → 세션이 끊겨도 끝난 조합은 다시 안 돌리고 이어서 진행 가능
- 순수 무가중 GBM+RF 조합(`gbm_rf_cv`)을 별도로 추가해, "가중치 자체의 효과"와 "MLP를 뺀 효과"를 분리해서 볼 수 있게 함
- 한글 폰트(NanumGothic) 자동 설치, GPU 감지 및 안내 메시지 추가

## 6. 핵심 발견 — LCC 개선 효과는 대부분 데이터 누수였다

v1.0의 `team_comparison.md`는 "LCC 보정으로 약 15% 개선(매뉴얼은 30%)"이라고 보고했었다. 그런데 F5(스케일러·특징선택을 train 폴드에만 fit)로 누수를 제거하고 F1의 방식대로 가중치를 1→10까지 스윕해서 다시 보니:

- **DS01-005 단거리**: 가중치를 올릴수록 RMSE가 18.29 → 18.55로 오히려 **더 나빠진다.**
- **DS03-012 단거리**: 17.11 → 16.87로 아주 소폭(약 1.4%) 개선되는 정도이고, v1.0이 보고했던 19.8% 개선과는 거리가 멀다.

즉, v1.0에서 관찰됐던 "LCC 가중치를 주면 좋아진다"는 결과는 **실제 효과가 아니라 스케일러/특징선택이 테스트 데이터를 미리 봐서 생긴 착시**였을 가능성이 높다. 데이터 누수를 없애자 효과가 사실상 사라지거나 뒤집혔다.

이건 `team_comparison.md`에 남겼던 팀원 질문 1번("Stage 2 방식이 다른 것 같은데 확인해달라")에 대한 답이기도 하다 — 방식(Medium+Long 선학습 후 Short fine-tuning) 차이가 아니라 **평가 코드의 누수**가 원인이었다.
